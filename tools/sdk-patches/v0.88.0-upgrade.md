# SDK v0.88.0 compatibility review

The patched SDK is based on public release `v0.88.0`, commit
`e7b0f118a08dda7cd97b699f9b7b7eccc3899ca8`. Generation uses the pinned
Speakeasy `1.808.1`. The SDK branch is
`patch/v0.88.0/targeted-patch-defaults`, commit
`df9d11baeab7bcdcab870cd35c19d14294ed2e49`, pushed to `origin`. kongctl
consumes it through `v0.88.1-0.20261116190824-df9d11baeab7`; this is a
patched v0.88.0 commit, not a v0.88.1 release. The bundle provenance records
kongctl commit `330c6b545feda75f9799f39366dab51e41d19740` (later amended by
`a955c838` to drop the dead `portal_agent` wire-test cases found during
generation; both are carried in the snapshot).

The gap from the previously consumed `v0.84.1-0.20261112154232-92b33d2ef4fd`
(a patched v0.84.0 commit) to `v0.88.0` is only nine upstream commits: six
automated OAS-regeneration PRs (#459–#465), one dependency bump, one CI
change, and `4d0e77b7` ("fix identity realms omitzero tag in
AIGWKeyAuthGeneratedConfig", #458).

## Kong Identity regional routing (kongctl#2790) — resolved natively

Through `v0.87.0`, generated code hardcoded `operations.XxxServerList[0]`
(`us.api.konghq.com`) as the base URL for 81 Kong Identity operations
(directories, principals, groups, credentials, Trusted IdPs, Token Vault
keys/providers/credentials), overriding `--base-url`/`--region`/
`konnect.region`. `Kong/platform-api#4038` ("fix: tooling assuming global
endpoint for kong-identity") removed the hardcoded global server blocks from
the OAS on 2026-11-16. The `v0.88.0` OAS update (generated minutes later)
picked this up: all 81 operations now resolve their base URL from SDK
configuration like every other operation. Verified directly: `v0.87.0` still
has 81 occurrences of `ServerList[0]` across the nine affected files;
`v0.88.0` has zero, and a full regional-routing regression (every operation
on all nine affected API groups, against US/EU/AU/custom base URLs, with and
without a per-call server override) passes against vanilla `v0.88.0` with no
patch applied.

This supersedes the in-progress temporary overlay on SDK branch
`patch/v0.84.0/identity-regional-routing` and kongctl branch
`id-patch-region-v2`, both started earlier the same day before the upstream
fix landed. Neither should be merged — the overlay would fail strict
application against `v0.88.0` (exactly as its own README warned:
"Once upstream removes these operation servers, strict application must
fail"). The regional-routing wire regression itself is worth keeping, so it
was ported as a plain test (no overlay) —
`identity_regional_routing_test.go.txt` — added to the bundle in commit
`f77bd9b3`.

## Breaking and behavioral changes

- **AI Gateway MCP Server `route` is now required in all three config
  modes** (`upstream-server`, `passthrough-listener`,
  `conversion-listener`) — **in both the request and the response
  schema.** Confirmed directly against `platform-api`'s OAS:
  `AIGatewayMCPServerConfigBaseProperties` (`required: [route]`) is
  inherited by `AIGatewayMCPServerUpstreamServerConfig` and the
  listener-mode config schemas, and `AIGatewayMCPServerUpstreamServerResponse`
  reuses that same config schema unchanged — there is no separate, more
  lenient response variant. The generated
  `AIGatewayMCPServerUpstreamServerConfigOutput.UnmarshalJSON` (and the
  listener-mode equivalents) enforces this on every `list`/`get` decode, not
  only on writes. kongctl's declarative schema and planner already fully
  support `route` (most MCP server tests already set it); nine unit tests
  whose fixtures predated this requirement were updated to include a
  minimal `route` block so they keep exercising their actual logic.

  **Needs intervention — two distinct risks, neither fixed here:**
  1. `AIGatewayMCPServerResource` embeds
     `kkComps.CreateAIGatewayMCPServerRequest` directly, so the loader's
     `json.Unmarshal` already fails a manifest
     that omits `route` in `upstream-server`/`conversion-listener` mode —
     confirmed against the generated
     `AIGatewayMCPServerUpstreamServerConfig.UnmarshalJSON`'s required list
     (`["route", "url", "tools_cache_ttl_seconds"]`). A prior version of
     this note said such a config "passes `kongctl plan` today and only
     fails when applied against the live API" — that was wrong; it fails
     at load, before planning starts, with the SDK's generic
     missing-required-field error rather than a kongctl-styled one.
     Replacing that message with a clearer, resource-specific one (per this
     repo's "Required API fields must be explicitly stated in declarative
     manifests" convention) is a reasonable follow-up, but it is a
     cosmetic/UX change, not a correctness gap — not scoped here.
  2. `route` was optional in `v0.84.0`'s schema. Any MCP server created
     before the field became required, and still lacking one, would now
     fail the SDK's strict decode on `list`/`get` — breaking `plan`,
     `dump`, and `get` for the whole gateway, not just that one server.
     Whether this is reachable depends on whether `platform-api` backfilled
     `route` for pre-existing records when the requirement landed; kongctl
     has no live organization predating the change to verify this against.
     Tolerating a missing `route` in the SDK's decode would mean silently
     accepting responses that violate the API's own documented schema
     contract — a `platform-api` data-migration question to confirm, not a
     kongctl-side decode bug to patch around speculatively.

- **`ControlPlaneConfig` response fields became optional pointers with
  documented defaults.** `ClusterType`, `AuthType`, and `CloudGateway`
  changed from required values (`ControlPlaneClusterType`,
  `ControlPlaneAuthType`, `bool`) to
  `*ControlPlaneClusterType`/`*ControlPlaneAuthType`/`*bool`, each carrying
  a literal `default:` tag (`CLUSTER_TYPE_CONTROL_PLANE`,
  `pinned_client_certs`, `false`) confirmed in the OAS diff. In practice the
  API still always returns a value; this only matters for nil-safety. Updated
  nine call sites across `adopt`, `dump`, `declarative/export`,
  `declarative/planner`, and `declarative/fieldcontracts` (plus their tests)
  to dereference safely. Equality checks against
  `ControlPlaneClusterTypeClusterTypeControlPlaneGroup` treat nil as "not a
  group" (correct, since the default is a different value). `fieldcontracts`
  gives nil two separate meanings depending on the consumer: `dump`/export
  still treats it as the pre-upgrade empty-string zero value (so a `dump`
  continues to omit `cluster_type`/`auth_type` when the API default
  applies, preserving the existing "omit values equal to the API default"
  contract); `plan`'s comparison path instead resolves nil to the
  documented default before comparing, so a declaration that matches that
  default does not show as perpetual drift against a response that bypassed
  the SDK's own default-fill (e.g. an explicit `null`).

- **AI Gateway Agent `config.url` is no longer required by the API.**
  `CreateAIGatewayAgentRequestConfig.URL`/
  `UpdateAIGatewayAgentRequestConfig.URL` changed from `string` to
  `*string`; the OAS diff shows `required: [url]`
  removed from the `config` sub-schema (agents can now be configured via
  `upstream`/`route`/`proxy` alone, which kongctl's schema already supports
  for other purposes). kongctl's own "config.url is required" validation
  (resource and executor layers) was deliberately left unchanged — only the
  compile errors were fixed with nil-safe equivalents — to avoid silently
  loosening what `kongctl plan` accepts.

  **Needs intervention:** relaxing kongctl's validation to allow
  `upstream`-only agent configs (matching the new API contract) is a product
  decision, not a mechanical fix, and hasn't been made here.

- **Portal Identity Provider OIDC config renamed and gained a field.**
  `PortalOIDCIdentityProviderConfig` (create path) was renamed to
  `PortalOIDCIdentityProviderConfigInput`, and the equivalent response-side
  type lost its `Output` suffix (`PortalOIDCIdentityProviderConfigOutput` →
  `PortalOIDCIdentityProviderConfig`). Both gained a new optional
  `BackchannelLogout` field that kongctl's generic
  `OIDCIdentityProviderConfig`/`OIDCIdentityProviderConfigOutput` source types
  don't carry. `internal/konnect/helpers/portal_identity_providers.go` and
  `internal/declarative/state/client.go` previously did a raw struct-to-struct
  type conversion between these (relying on identical field layout); both now
  field-map explicitly, leaving `BackchannelLogout` unset.

  **New capability, not yet exposed:** upstream added OIDC back-channel
  logout support for Portal identity providers. kongctl does not expose it
  declaratively. No action taken — flagging for separate scoping if desired.

- **Portal AI settings `portal_agent` feature removed entirely.** The
  `display_name`/`audience` sub-schema and its backing types
  (`PortalAgentDisplayNameNullable`, `PortalAgentAudienceNullable`) are gone
  from `v0.88.0`'s OAS and generated code. kongctl never referenced this
  feature. The `portal-ai-settings-patch-defaults.yaml` overlay's two dead
  actions targeting those removed schemas were dropped (the
  `mcp_server.write_operations_enabled` action is untouched); three
  corresponding dead test cases were removed from
  `portal_ai_settings_defaults_test.go.txt`.

- **Identity-realms `omitzero` fix (PR #458) landed upstream, and the file it
  lived in was renamed.** `AIGWKeyAuthGeneratedConfig` was restructured into
  `AIGatewayAuthStrategyKeyAuthConfig`/`...ResponseConfig` in new files; both
  already carry `json:"identity_realms,omitzero"` natively. kongctl's
  existing patch entry (`models/components/aigwkeyauthgeneratedconfig.go`,
  `optional_file: true`) now silently no-ops because that file no longer
  exists — exactly the "legacy config-file patch is skipped when absent,
  newer SDKs use flexible configs" scenario the bundle's README already
  documents. Left untouched; its wire test
  (`identity_realms_test.go.txt`) only exercises outer wrapper types and is
  unaffected by the rename.

- **OIDC auth-strategy config file split, same pattern as KeyAuth.**
  `AIGWOpenIDConnectGeneratedConfig`/`...GeneratedConfigOutput` (previously
  sharing one file) split into `AIGatewayAuthStrategyOpenIDConnectConfig`
  (`aigatewayauthstrategyopenidconnect.go`) and
  `AIGatewayAuthStrategyOpenIDConnectResponseConfig`
  (`aigatewayauthstrategyopenidconnectresponse.go`). The
  `upstream_access_token_header` patch (kongctl#2765 follow-up) was re-ported
  to the two new files/types with newly extracted literal before/after text;
  no behavioral change. Two kongctl test files
  (`explain_conformance_test.go`, `ai_gateway_auth_strategies_test.go`)
  referenced the old type names directly and were updated to the new ones.
  The `TestKongctlOIDCConfigWirePresence` wire regression (recorded against
  unmodified `v0.84.0` models) passed unchanged against `v0.88.0`, confirming
  no other OIDC config default value changed in this range — only this one
  field's representation moved.

- **New `TrustedIdpJit.Mapping.Identifier` field, default `"sub"`, no
  `omitempty`.** Not present in `v0.84.0`.
  `internal/konnect/identitytrust/configuration.go`'s `NormalizeJIT` treats
  an omitted identifier and an explicit `"sub"` as equivalent (matching its
  existing treatment of other empty-mapping fields), so request/response
  diffing isn't tripped by the server filling in its own documented
  default. Recorded in the dump-defaults golden inventory as
  `trusted_idps.jit.mapping.identifier` /
  `identity_trusted_idp.jit.mapping.identifier` = `"sub"`, source `sdk`.

  **Fixed as part of this upgrade — silent re-key on partial updates.**
  Because the field lacks `omitempty`, every marshal/unmarshal of
  `TrustedIdpJitMapping` fills a nil identifier with `"sub"`, including the
  manifest's own first parse — so "declared `sub`" and "never declared" are
  indistinguishable by the time the field reaches the executor. A PUT
  replaces the whole `jit` object, so a declaration that only changes
  `jit.mapping.email` (say) would resend this always-filled-in `"sub"` and
  silently re-key principals provisioned under a remote `identifier` like
  `"oid"`. `identity_trusted_idp_adapter.go`'s `Update` now preserves a live,
  non-`"sub"` identifier whenever the declared one is nil or `"sub"`,
  consistent with `NormalizeJIT`'s existing equivalence rule. Trade-off: an
  explicit declared `identifier: sub` intended to reset away from a custom
  value is, by the same indistinguishability, also treated as "preserve the
  live value" — matching the equivalence this package already established
  for diffing, not a new inconsistency, but worth knowing if that reset is
  ever genuinely needed.

- **AI Gateway key-auth `anonymous` moved from the shared config to a
  response-only type.** `AIGWKeyAuthGeneratedConfig.Anonymous` (shared
  request/response in `v0.84.0`) is absent from the new
  `AIGatewayAuthStrategyKeyAuthConfig` (request); it now lives only on
  `AIGatewayAuthStrategyKeyAuthResponseConfig`. The planner's update path
  merges the observed config onto the declared one to preserve fields the
  user didn't touch, so without a fix any key-auth strategy update would
  resend the observed `anonymous` and fail the executor's dropped-field
  check (`contains fields not supported by the current SDK: config.anonymous`).
  Dumping a key-auth strategy also exported the raw response's `anonymous`,
  so re-applying a dump failed the same way on **create**. **Fixed as part
  of this upgrade:** `mergeAIGatewayAuthStrategyConfig` now drops
  known response-only fields per auth-strategy type before merging, and the
  AI Gateway Auth Strategy dump strips `anonymous` from key-auth exports.

- `models/sdkerrors`, `retry`, `optionalnullable`, and `pkg/metadata` have
  zero diff between `v0.84.0` and `v0.88.0`. No new error types, no behavior
  changes in those packages.

## PATCH compatibility and assumptions

All existing targeted overlays and generated-code replacements apply
cleanly against `v0.88.0` except the two dead `portal_ai_settings` overlay
actions (removed above). The `identity-realms` omitzero patch correctly
no-ops. The OIDC `upstream_access_token_header` patch was re-targeted at the
split files. No new request defaults were discovered in the OAS diff beyond
`trusted_idps.jit.mapping.identifier`, which is additive and normalized
rather than patched.

## Local validation

- SDK regeneration, compilation, and `go vet` pass. SDK patch wire
  regressions, `kongctl_sdk_patched`-tagged construction tests, and
  model/internal/package tests pass. `make test.unit` passes with the race
  detector.
- kongctl `go fix ./...` (no changes), `make format` (no changes after
  applying), `make build`, `make lint` (0 issues), `make test`, and
  `make test-integration` all pass.
- `make test-extension-go` passes (`GOFLAGS=-buildvcs=false` needed locally
  for Go VCS stamping, same as the v0.84.0 upgrade). The example module's
  `go mod tidy -diff` is empty; its selected SDK is the patched pseudo-version
  with no replace directive.
- No live E2E scenarios ran locally; CI E2E is expected to confirm live
  service behavior, in particular the Kong Identity regional-routing fix
  against a real EU/AU organization.
